每个技能应该包含以下部分：

```markdown

## 概览
- 一句话定义技能的核心目的
- 说明触发条件和适用场景

## 触发条件
- 条件1：具体描述
- 条件2：具体描述

## 执行步骤

### 步骤1：步骤名称
- 子步骤1
- 子步骤2
- 子步骤3

### 步骤2：步骤名称
...

## 输出格式
```<language>
<标准输出模板>
```

## 关键原则
- 原则1
- 原则2

## 反模式
- ❌ 错误做法
- ✅ 正确做法
```

## 编写步骤

### 步骤1：定义技能边界

明确技能的职责范围，避免技能重叠或遗漏。

**问题清单**：
1. 这个技能解决什么具体问题？
2. 何时应该触发这个技能？
3. 技能的输入和输出是什么？
4. 与其他技能的关系是什么？

**示例**：
```
技能：systematic-debugging

问题：如何系统化地调试bug？
输入：错误信息、复现步骤、代码
输出：根因分析、修复方案、验证结果
关系：依赖brainstorming的提问技巧
```

### 步骤2：确定触发条件

列出技能触发的典型场景，确保智能体能自动识别。

**触发条件模板**：
```
- 用户表达：<用户可能的表述>
- 智能体检测：<内部状态或上下文>
- 时机描述：<什么时候应该激活>
```

**示例**：
```
触发条件：
- 用户表达："遇到了bug"、"代码报错"、"功能不正常"
- 智能体检测：捕获到异常、测试失败、性能下降
- 时机描述：任何需要诊断和修复问题的时候
```

### 步骤3：设计执行步骤

将技能执行过程分解为清晰的步骤，每个步骤都有明确的输出。

**步骤设计原则**：
1. 步骤顺序逻辑清晰
2. 每个步骤有明确的入口和出口
3. 步骤之间有清晰的依赖关系
4. 避免循环和歧义

**示例**：
```
执行步骤：
1. 识别症状 → 输出：症状清单
2. 定位根因 → 输出：根因分析
3. 验证修复 → 输出：修复结果
4. 防止复现 → 输出：长期措施
```

### 步骤4：定义输出格式

为每个技能定义标准输出格式，确保一致性。

**输出格式要素**：
- 结构化（如Markdown、JSON）
- 包含所有关键信息
- 易于阅读和解析
- 包含验证状态

**示例**：
```markdown
# 调试报告

## 问题摘要
...

## 症状识别
...

## 根因定位
...

## 修复验证
...

## 防止复现
...
```

### 步骤5：编写关键原则

总结技能的核心原则，指导正确使用。

**原则类型**：
- 强制性原则（必须遵守）
- 推荐性原则（建议遵守）
- 禁止性原则（禁止违反）

**示例**：
```
关键原则：
- 不要随机猜测，使用系统化方法（强制性）
- 验证每个假设，不要跳过（强制性）
- 修复后必须验证（强制性）
- 长期措施比临时修复更重要（推荐性）
```

### 步骤6：识别反模式

列出常见错误和正确做法，帮助避免陷阱。

**反模式格式**：
```
❌ 错误做法：描述错误的做法
✅ 正确做法：描述正确的做法
```

**示例**：
```
反模式：
❌ 错误做法：看到错误就立即修改代码
✅ 正确做法：先分析根本原因，再修复

❌ 错误做法：修复后不验证
✅ 正确做法：修复后必须运行完整测试
```

## 最佳实践

### 1. 保持简洁

- 每个技能专注一个核心能力
- 避免包含过多细节
- 将复杂逻辑拆分为多个技能

**示例**：
```
❌ 不好：一个技能包含调试、测试、审查等多个能力
✅ 好：systematic-debugging, test-driven-development, requesting-code-review各司其职
```

### 2. 使用标准格式

- 使用统一的Markdown格式
- 输出格式保持一致
- 使用标准标题层级

### 3. 提供完整示例

- 每个步骤提供完整示例
- 示例应真实可运行
- 包含常见边界情况

### 4. 明确依赖关系

- 说明技能间的依赖
- 指出需要前置技能
- 标注输出产物

**示例**：
```
依赖：
- 前置技能：brainstorming
- 输入产物：docs/design.md
- 输出产物：docs/implementation-plan.md
```

### 5. 可测试性

- 技能应该是可验证的
- 每个步骤都有明确检查点
- 提供验证清单

## 测试指南

### 测试类型

1. **单元测试**
   - 测试单个技能的独立功能
   - 验证输出格式正确
   - 检查关键原则遵守

2. **集成测试**
   - 测试技能之间的协作
   - 验证工作流完整性
   - 检查依赖关系

3. **端到端测试**
   - 模拟真实使用场景
   - 验证整体效果
   - 检查用户体验

### 测试模板

```python
# test_systematic_debugging.py
import pytest
from superpowers.skills import systematic_debugging

def test_identify_symptoms():
    """测试症状识别步骤"""
    error_info = {
        'error': 'DatabaseError: connection timeout',
        'context': {'user_id': 12345}
    }

    symptoms = systematic_debugging.identify_symptoms(error_info)

    assert symptoms['error_type'] == 'DatabaseError'
    assert symptoms['user_id'] == 12345
    assert 'traceback' in symptoms

def test_locate_root_cause():
    """测试根因定位步骤"""
    symptoms = {'error_type': 'DatabaseError', 'location': 'db.py:23'}

    root_cause = systematic_debugging.locate_root_cause(symptoms)

    assert 'hypothesis' in root_cause
    assert 'verified' in root_cause
    assert 'root_cause' in root_cause

def test_verify_fix():
    """测试修复验证步骤"""
    fix = {
        'code': '# fix code',
        'test': 'test function'
    }

    result = systematic_debugging.verify_fix(fix)

    assert result['status'] in ['passed', 'failed']
    assert 'execution_time' in result
```

### 测试清单

- [ ] 输出格式符合标准
- [ ] 所有关键原则遵守
- [ ] 无反模式违反
- [ ] 依赖关系正确
- [ ] 边界情况处理
- [ ] 错误处理完善

## 示例：创建新技能

### 场景
创建一个"代码格式化"技能。

### 步骤1：定义边界
```
技能名称：code-formatting

问题：如何确保代码格式一致？
输入：代码文件
输出：格式化后的代码
关系：在requesting-code-review之前调用
```

### 步骤2：确定触发条件
```
触发条件：
- 用户表达："格式化代码"、"代码风格不统一"
- 智能体检测：代码不符合格式规范
- 时机描述：提交代码审查之前
```

### 步骤3：设计执行步骤
```
执行步骤：
1. 检测格式问题 → 输出：问题清单
2. 应用格式化规则 → 输出：格式化后的代码
3. 验证格式 → 输出：验证结果
```

### 步骤4：定义输出格式
```markdown
# 代码格式化报告

## 检测到的问题
- 格式问题1：行长度超过100字符
- 格式问题2：缩进不一致

## 格式化结果
- 文件：src/module.py
- 修改行数：15
- 状态：✅ 已格式化

## 验证结果
- [x] Black格式化通过
- [x] Flake8检查通过
```

### 步骤5：编写关键原则
```
关键原则：
- 使用标准格式化工具（Black）
- 自动修复，无需手动调整
- 保持代码语义不变
```

### 步骤6：识别反模式
```
反模式：
❌ 错误做法：手动格式化
✅ 正确做法：使用自动化工具

❌ 错误做法：只格式化部分代码
✅ 正确做法：格式化整个文件
```

### 最终技能文档

```markdown
# code-formatting - 代码格式化

## 概览
使用自动化工具确保代码格式一致，遵循项目规范。

## 触发条件
- 用户表达："格式化代码"、"代码风格不统一"
- 智能体检测：代码不符合格式规范
- 时机描述：提交代码审查之前

## 执行步骤

### 步骤1：检测格式问题
运行格式化工具检测问题：
```bash
black --check src/
flake8 src/
```
输出：问题清单

### 步骤2：应用格式化规则
自动修复格式问题：
```bash
black src/
autopep8 --in-place src/
```
输出：格式化后的代码

### 步骤3：验证格式
验证格式化结果：
```bash
black --check src/
flake8 src/
```
输出：验证结果

## 输出格式
```markdown
# 代码格式化报告

## 检测到的问题
- 格式问题1：行长度超过100字符
- 格式问题2：缩进不一致

## 格式化结果
- 文件：src/module.py
- 修改行数：15
- 状态：✅ 已格式化

## 验证结果
- [x] Black格式化通过
- [x] Flake8检查通过
```

## 关键原则
- 使用标准格式化工具（Black）
- 自动修复，无需手动调整
- 保持代码语义不变

## 反模式
❌ 错误做法：手动格式化
✅ 正确做法：使用自动化工具

❌ 错误做法：只格式化部分代码
✅ 正确做法：格式化整个文件
```

## 总结

编写技能的关键点：
1. **明确边界**：一个技能专注一个能力
2. **标准格式**：使用统一的模板结构
3. **完整示例**：提供可运行的示例代码
4. **可测试性**：每个技能都应该可验证
5. **文档优先**：清晰胜过简洁

遵循这些原则，可以创建出高质量、易维护的Superpowers技能。
