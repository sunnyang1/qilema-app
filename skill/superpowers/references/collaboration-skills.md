## adversarial-review - 对抗性审查（增强版）

### 概览
强制推理技术，防止懒惰的"看起来不错"审查。要求审查者必须找到问题，零发现触发重新分析。现已集成 code-review-expert 的结构化审查框架，支持 P0-P3 优先级分级和 6 个审查维度。

### 核心原则

**强制规则**：必须找到问题，不允许"看起来不错"

零发现触发重新分析或解释原因。

### 为什么有效

正常审查受确认偏差影响。你浏览工作，没有突出内容，然后批准它。"找问题" mandate打破了这种模式：

- **强制彻底性**：在查看足够深以发现问题之前不能批准
- **捕获缺失内容**："什么不在这里？"成为自然问题
- **提高信号质量**：发现具体且可操作，不是模糊的担忧
- **信息不对称**：使用新鲜上下文运行审查（无原始推理访问），以便评估工件而非意图

### 使用位置

对抗性审查出现在整个Superpowers工作流中 - 代码审查、实施就绪检查、规格验证等。有时是必需步骤，有时是可选的（如高级启发或Party模式）。模式适应任何需要审查的工件。

### 人工过滤必需

因为AI被指示找到问题，它会找到问题——即使它们不存在。预期会有误报：

- 包装成问题的挑剔
- 意图的误解
- 纯粹的幻觉担忧

**你决定什么是真实的。** 审查每个发现，驳回噪音，修复重要的东西。

### 优先级分级（P0-P3）

| 级别 | 名称 | 描述 | 行动 |
|------|------|------|------|
| **P0** | Critical | 安全漏洞、数据丢失风险、正确性 bug | 必须阻止合并 |
| **P1** | High | 逻辑错误、重大 SOLID 违规、性能回归 | 合并前应该修复 |
| **P2** | Medium | 代码异味、可维护性关注、轻微 SOLID 违规 | 在此 PR 中修复或创建后续任务 |
| **P3** | Low | 风格、命名、次要建议 | 可选改进 |

### 6 个审查维度

1. **SOLID 原则** - 检测 SRP、OCP、LSP、ISP、DIP 违规
2. **安全与可靠性** - XSS、注入、SSRF、竞态条件、AuthN/AuthZ 漏洞
3. **性能** - N+1 查询、CPU 热点、缺少缓存、内存问题
4. **错误处理** - 吞并异常、异步错误、缺少边界检查
5. **边界条件** - Null/undefined 处理、空集合、数值边界、off-by-one
6. **移除规划** - 识别死代码，提供安全删除或延迟删除计划

详见：[code-review-checklist.md](code-review-checklist.md)

### 输出格式

使用标准化的输出模板，确保审查报告一致且可操作：

详见：[review-output-template.md](review-output-template.md)

### 示例

代替：

> "身份验证实施看起来合理。批准。"

对抗性审查产生：

```markdown
## Code Review Summary

**Files reviewed**: 2 files, 89 lines changed
**Overall assessment**: REQUEST_CHANGES

---

## Findings

### P0 - Critical

1. **[src/auth.ts:45]** SQL 注入漏洞
   - 用户输入直接拼接进 SQL 查询，允许注入攻击
   - 建议修复：使用参数化查询

### P1 - High

2. **[src/auth.ts:78]** 竞态条件 - Check-Then-Act 模式
   - 余额检查后跟扣款，两个并发请求可能导致透支
   - 建议修复：使用数据库事务和原子操作

3. **[src/auth.ts:123]** 违反 SRP 原则
   - Auth 类同时处理 HTTP、DB 和业务逻辑
   - 建议修复：拆分为独立层

### P2 - Medium

4. **[src/utils.ts:56]** 吞并异常
   - 空的 catch 块隐藏潜在错误
   - 建议修复：记录错误并适当处理

### P3 - Low

5. **[src/config.ts:12]** 魔术数字
   - 硬编码的超时值 `3000` 没有命名常量
   - 建议修复：定义为 `REQUEST_TIMEOUT_MS`

---

## Next Steps

我发现了 5 个问题（P0: 1, P1: 2, P2: 1, P3: 1）。

**您希望如何继续？**

1. **修复所有** - 我将实施所有建议的修复
2. **仅修复 P0/P1** - 解决关键和高优先级问题
3. **修复特定项目** - 告诉我要修复哪些问题
4. **无更改** - 审查完成，无需实施

请选择一个选项或提供具体说明。
```

第一次审查可能遗漏安全漏洞。第二次捕获了五个。

### 迭代和收益递减

在解决发现后，考虑再次运行它。第二轮通常会捕获更多。第三轮并不总是没用。但每轮都需要时间，最终会达到收益递减——只有挑剔和虚假发现。

### 实施步骤

#### 步骤1：准备审查

1. **获取工件**
   - 代码文件
   - 设计文档
   - PRD或规格
   - 实施计划

2. **使用新鲜上下文**
   - 不访问原始推理
   - 仅评估工件本身
   - 避免受意图影响

#### 步骤2：执行审查

1. **采用批判性立场**
   - 假设问题存在
   - 寻找弱点
   - 不要相信任何"看起来合理"

2. **加载检查清单**
   - 读取 [code-review-checklist.md](code-review-checklist.md)
   - 遍历 6 个审查维度
   - 检查每个维度的具体项目

3. **按优先级分类问题**
   - P0（Critical）：安全漏洞、数据丢失风险、正确性 bug
   - P1（High）：逻辑错误、重大 SOLID 违规、性能回归
   - P2（Medium）：代码异味、可维护性关注、轻微 SOLID 违规
   - P3（Low）：风格、命名、次要建议

4. **查找缺失内容**
   - 问"什么不在这里？"
   - 检查边界情况
   - 检查错误路径
   - 检查依赖项

#### 步骤3：评估发现

1. **验证每个发现**
   - 这是真实问题吗？
   - 还是误解？
   - 还是幻觉？

2. **优先级排序**
   - P0：必须立即修复
   - P1：应该修复
   - P2：可以延后或创建后续任务
   - P3：可选改进

3. **提供解决方案**
   - 对于每个问题，提供具体修复建议
   - 解释为什么这是问题
   - 解释如何修复

#### 步骤4：生成报告

使用 [review-output-template.md](review-output-template.md) 中的标准格式生成审查报告。

报告必须包含：
- 审查摘要（文件数、行数、整体评估）
- 按优先级分组的问题列表（P0-P3）
- 移除/迭代计划（如适用）
- 额外建议（可选）
- 后续步骤（等待用户确认）

### 人工评估

- [ ] 问题1：确认是真实问题
- [ ] 问题2：确认是真实问题
- [ ] 问题3：确认是真实问题
- [ ] 问题4：确认是真实问题
- [ ] 问题5：误报，忽略
```

### 人工过滤

由于AI被指示找到问题，它会找到问题——即使它们不存在。预期会有误报：

**误报类型**：
1. **包装成问题的挑剔**：代码风格、命名约定等非关键问题
2. **意图的误解**：不理解设计意图，认为有问题
3. **幻觉担忧**：完全不存在的问题

**过滤策略**：
1. 审查每个发现
2. 判断这是真实问题还是误报
3. 对于误报，标记为"忽略"
4. 对于真实问题，优先级排序并修复

### 迭代使用

**第一轮审查**：
- 发现初始问题
- 修复关键问题

**第二轮审查**：
- 通常会捕获更多问题
- 特别是在修复引入新问题后

**第三轮审查**：
- 可能仍有价值
- 但收益递减
- 大多是挑剔和虚假发现

**何时停止**：
- 连续2轮无新发现
- 或问题都是LOW级别挑剔
- 或时间成本超过收益

### 最佳实践

1. **不要跳过对抗性审查**：即使是小任务也要执行
2. **使用新鲜上下文**：避免受原始推理影响
3. **人工评估每个发现**：不要自动接受所有发现
4. **优先级排序**：先修复HIGH和MEDIUM问题
5. **记录发现**：保存审查报告以供参考
6. **迭代使用**：重要工件使用多轮审查

### 应用场景

- **代码审查**：TDD实施后、提交前
- **设计审查**：架构设计完成后
- **PRD审查**：PRD生成后、实施前
- **实施就绪检查**：进入自主循环前
- **集成测试审查**：集成测试完成后
- **发布审查**：发布前

## requesting-code-review - 代码审查（增强）

### 概览
在任务之间进行系统化代码审查，对照实施计划检查，强制发现问题（对抗性审查）。

### 触发条件
- 单个任务完成
- 子智能体完成其工作
- 准备进入下一个任务

### 执行步骤

#### 步骤1：对照计划审查
1. 读取 `docs/implementation-plan.md`
2. 检查是否实现了所有计划内容
3. 检查是否有遗漏或超出范围

#### 步骤2：对抗性审查（新增）

**核心规则**：必须找到问题，不允许"看起来不错"

1. **采用批判性立场**
   - 假设问题存在并找到它们
   - 查找缺失内容
   - 评估工件而非意图

2. **执行对抗性审查**
   - 详见 [adversarial-review](#adversarial-review---对抗性审查) 部分

3. **分级问题**
   - HIGH：安全漏洞、数据丢失、重大性能问题
   - MEDIUM：代码质量、可维护性、错误处理
   - LOW：命名、魔术数字、注释

4. **提供解决方案**
   - 每个问题提供具体修复建议
   - 解释为什么这是问题
   - 解释如何修复

#### 步骤3：质量检查清单

- [x] 命名清晰且一致
- [x] 函数单一职责
- [x] 错误处理完善
- [x] 无重复代码（DRY原则）
- [x] 测试覆盖充分
- [x] 代码可读性良好

#### 步骤4：严重性问题识别
- 仅报告阻碍继续开发的严重问题
- 轻微问题可以记录但不阻塞
- 提供具体的修复建议

#### 步骤5：生成审查报告

```markdown
# 代码审查报告（增强版）

## 审查范围
- 文件：src/models/user.py
- 计划：docs/implementation-plan.md（第3行-第5行）

## 对照计划检查
- [x] 创建了User类
- [x] 包含id字段
- [x] 包含name字段
- [x] 包含email字段
- [ ] 缺少password字段（计划中有）

## 对抗性审查结果

### 发现的问题

1. **HIGH** - `models/user.py:47` - email字段缺少格式验证
   - 风险：无效数据入库
   - 建议：添加email格式验证函数

2. **HIGH** - 密码明文存储
   - 风险：严重安全漏洞
   - 建议：使用bcrypt哈希密码

3. **MEDIUM** - `models/user.py:23` - __init__方法过长（15行）
   - 风险：可维护性差
   - 建议：提取字段验证逻辑到私有方法

4. **MEDIUM** - 无输入清理
   - 风险：XSS攻击
   - 建议：添加输入清理函数

5. **LOW** - 缺少类型注解
   - 风险：可读性差
   - 建议：添加完整类型注解

## 代码质量检查

### 严重问题
1. **密码明文存储** - 必须修复
2. **email格式验证缺失** - 必须修复

### 中等问题
1. **__init__方法过长** - 应该修复
2. **无输入清理** - 应该修复

### 轻微问题
1. **缺少类型注解** - 可以延后

## 审查结论

发现2个HIGH问题、2个MEDIUM问题、1个LOW问题

## 阻塞状态
⚠️ 阻塞：必须修复HIGH和MEDIUM问题后才能继续下一个任务

## 后续行动
1. 使用bcrypt哈希密码
2. 添加email格式验证
3. 提取__init__方法逻辑
4. 添加输入清理函数
```

#### 步骤6：重新审查

在修复问题后，重新执行对抗性审查：

1. 修复所有HIGH和MEDIUM问题
2. 重新运行对抗性审查
3. 检查是否引入新问题
4. 确认所有问题已解决

### 输出格式

```markdown
# 代码审查报告

## 审查范围
- 文件：src/models/user.py
- 计划：docs/implementation-plan.md

## 对照计划检查
- [x] 创建了User类
- [x] 包含id字段
- [x] 包含name字段
- [x] 包含email字段
- [ ] 缺少password字段（计划中有）

## 对抗性审查结果

### 发现的问题
1. HIGH - email字段缺少格式验证
2. HIGH - 密码明文存储
3. MEDIUM - __init__方法过长
4. MEDIUM - 无输入清理
5. LOW - 缺少类型注解

## 审查结论
发现2个HIGH问题、2个MEDIUM问题、1个LOW问题

## 阻塞状态
⚠️ 阻塞：必须修复HIGH和MEDIUM问题后才能继续下一个任务
```

### 关键原则
- 严格对照计划，不超范围
- **对抗性审查：强制发现问题**
- 严重问题阻塞后续开发
- 提供具体修复建议
- 记录轻微问题但不阻塞

### 多智能体协作流程

#### 步骤1：问题陈述

你提出问题或任务：
```
"我们需要添加用户认证功能"
```

#### 步骤2：角色响应

**Product Manager**：
```
从产品角度，我需要澄清：
- 谁是目标用户？
- 认证方式偏好（邮箱/手机/第三方）？
- 安全级别要求？
- 是否需要单点登录（SSO）？
```

**Architect**：
```
从技术角度，我需要考虑：
- 使用JWT还是Session？
- 如何存储用户凭证？
- 如何处理密码重置？
- 如何实现OAuth集成？
```

**Developer**：
```
从实施角度，我建议：
- 使用bcrypt哈希密码
- 实现JWT认证
- 添加速率限制
- 使用HttpOnly Cookie
```

**UX Designer**：
```
从用户体验角度，我建议：
- 简化登录流程
- 支持"记住我"功能
- 提供密码强度指示器
- 友好的错误提示
```

**QA Engineer**：
```
从测试角度，我关注：
- 登录/注册流程测试
- 密码重置流程测试
- 安全测试（暴力破解、XSS）
- 性能测试（并发登录）
```

#### 步骤3：讨论和决策

角色之间讨论，达成共识：

```
Architect: 我建议使用JWT，因为无状态，易于扩展
Developer: 同意，但需要考虑token刷新机制
Product Manager: 好的，但需要考虑SSO需求吗？
Architect: 可以通过OAuth实现SSO
UX Designer: 需要简化SSO流程，减少用户摩擦
Developer: 可以实现自动token刷新
QA Engineer: 需要测试token过期和刷新流程
```

#### 步骤4：达成共识

最终达成共识：
- 使用JWT + HttpOnly Cookie
- bcrypt哈希密码
- 实现OAuth支持SSO
- 自动token刷新
- 简化登录流程

#### 步骤5：任务分解

基于共识，分解任务：

```
US-001: 创建用户模型（Developer）
US-002: 实现JWT认证（Developer）
US-003: 实现OAuth集成（Developer）
US-004: 设计登录界面（UX Designer）
US-005: 编写认证测试（QA Engineer）
US-006: 编写集成测试（QA Engineer）
```

### Party Mode示例

**场景：讨论认证服务故障**

**你**："团队，认证服务上周故障了3次。谁的责任？"

**Architect**：
```
设计是合理的 - 分布式认证有适当的回退机制。
如果实现偏离了规范...
```

**Developer**：
```
我完全按照架构文档实现。
规范没有考虑并发会话失效竞态条件。
```

**Product Manager**：
```
你们都错过了更大的问题 - 我们没有在PRD中验证会话管理需求。
这是我的错，没有捕获到。
```

**QA Engineer**：
```
我也应该在集成测试中捕获这个问题。
测试场景没有涵盖并发失效。
```

**结论**：
- 需要在PRD中明确会话管理需求
- 需要在架构文档中考虑竞态条件
- 需要在测试中覆盖并发场景

### 最佳实践

1. **明确角色分工**：每个角色有明确的职责和关注点
2. **尊重专业意见**：尊重每个角色的专业领域
3. **充分讨论**：充分讨论，达成共识
4. **记录决策**：记录讨论过程和决策结果
5. **持续改进**：基于反馈持续改进协作流程

### 应用场景

- **重大技术决策**：架构选择、技术栈选择
- **需求澄清**：理解复杂需求
- **设计审查**：审查设计文档
- **问题诊断**：诊断复杂问题
- **Sprint回顾**：回顾Sprint，总结经验

## 总结

协作技能强调：
1. **对抗性审查**：强制发现问题，不允许"看起来不错"
2. **角色化智能体**：明确的角色定义，专门的职责和关注点
3. **并行执行**：利用多智能体加速开发
4. **任务隔离**：每个任务独立，低耦合
5. **质量保证**：代码审查和验证机制
6. **协调管理**：主智能体负责整体协调
7. **迭代改进**：基于审查反馈持续优化
