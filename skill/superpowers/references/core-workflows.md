## brainstorming - 交互式设计细化

### 概览
在编码之前，通过结构化问题深入理解需求，避免过早进入实现细节。

### 触发条件
- 收到"实现X功能"的需求
- 智能体检测到用户正在讨论"构建"或"创建"某物

### 执行步骤

1. **停止编写代码**
   - 智能体检测到编码意图时立即暂停
   - 向用户提问以理解真实目标

2. **探索性问题**
   - "你真正想要解决什么问题？"
   - "这个功能的主要用户是谁？"
   - "成功看起来是什么样的？"
   - "有哪些约束条件或边界情况？"
   - "是否有替代方案或更简单的实现？"

3. **提出选项**
   - 展示2-3个不同的设计方案
   - 每个方案包含：优点、缺点、适用场景

4. **细化到可理解的程度**
   - 将设计分解为逻辑章节
   - 每个章节都可独立验证
   - 确保章节之间有清晰的依赖关系

5. **保存设计文档**
   - 将最终设计保存为 `docs/design.md`
   - 包含：需求描述、设计决策、技术选型、验收标准

### 输出格式
```markdown
# 功能名称设计文档

## 需求描述
- 用户问题：...
- 业务价值：...

## 设计方案
### 方案A：...
- 优点：...
- 缺点：...

### 方案B：...
- 优点：...
- 缺点：...

## 最终选择
选择方案X，理由：...

## 实施计划
1. 章节1：...
2. 章节2：...

## 验收标准
- [ ] 准则1
- [ ] 准则2
```

### 关键原则
- 不要假设理解了，必须提问
- 提出多个选项，让用户做决策
- 设计文档必须可执行，不能含糊

## using-git-workflows - Git分支管理

### 概览
为每个开发任务创建隔离的Git分支，确保主分支始终稳定。

### 触发条件
- 设计文档已确认
- 准备开始编码工作

### 执行步骤

1. **创建新分支**
   ```bash
   git checkout -b feature/<功能名称>
   # 或
   git checkout -b fix/<问题描述>
   ```

2. **验证环境**
   - 确认项目设置正确（依赖、配置文件）
   - 验证测试基线干净
   ```bash
   pytest  # 所有测试应该通过
   ```

3. **创建草稿文档**
   - 创建 `docs/implementation-plan.md`
   - 列出计划实现的所有文件和函数

4. **提交初始状态**
   ```bash
   git add docs/implementation-plan.md
   git commit -m "docs: add implementation plan for <功能>"
   ```

### 输出格式
```markdown
# 实施计划 - <功能名称>

## 分支
- 分支名：feature/<功能名称>
- 基于分支：main

## 环境验证
- [ ] 所有基线测试通过
- [ ] 依赖安装正确
- [ ] 配置文件正确

## 文件计划
- [ ] `src/module1/file1.py` - 说明
- [ ] `src/module1/file2.py` - 说明
- [ ] `tests/test_feature.py` - 测试文件

## 提交计划
每次完成一个原子任务后提交：
- 原则：小步提交，频繁提交
- 格式：`<type>: <description>`
  - type: feat, fix, test, refactor, docs
```

### 关键原则
- 每个功能有独立分支
- 分支命名清晰（feature/ 或 fix/）
- 环境验证必须通过
- 保存实施计划

## writing-plans - 任务分解（增强复杂度自适应）

### 概览
将复杂功能分解为原子任务，每个任务都有清晰的文件路径和验证步骤。根据复杂度评估动态调整任务粒度。

### 触发条件
- Git分支已创建
- 准备开始编码前
- 复杂度评估已完成

### 执行步骤

1. **识别任务边界**
   - 根据复杂度级别调整任务粒度
   - 任务之间有清晰的依赖关系
   - 每个任务有明确的文件路径

2. **编写任务清单**

   **简单项目（5-10分钟/任务）**：
   ```
   Task 1: 创建用户模型文件
   文件：src/models/user.py
   内容：定义User类，包含id, name, email字段
   时间：5-7分钟
   验证：pytest tests/models/test_user.py
   ```

   **中等项目（2-5分钟/任务）**：
   ```
   Task 1: 创建用户模型文件
   文件：src/models/user.py
   内容：定义User类，包含id, name, email字段
   时间：3分钟
   验证：pytest tests/models/test_user.py
   ```

   **复杂项目（1-3分钟/任务）**：
   ```
   Task 1: 创建User类骨架
   文件：src/models/user.py
   内容：定义User类，仅包含类定义
   时间：1分钟
   验证：pytest tests/models/test_user.py::test_user_class_exists

   Task 2: 添加id字段
   文件：src/models/user.py
   内容：添加id属性
   时间：1分钟
   验证：pytest tests/models/test_user.py::test_user_id_field
   ```

3. **估算时间**
   - 简单项目：5-10分钟/任务
   - 中等项目：2-5分钟/任务
   - 复杂项目：1-3分钟/任务
   - 超过预估时间的任务需要进一步分解

### 输出格式

**简单项目示例**：
```markdown
# 任务清单 - <功能名称>

## 复杂度级别：简单
## 任务粒度：5-10分钟/任务

## 任务1：创建数据模型
- 文件：`src/models/user.py`
- 时间：5-7分钟
- 步骤：
  1. 创建文件 src/models/user.py
  2. 定义 User 类，包含 id, name, email 字段
  3. 添加 __repr__ 方法
- 验证：pytest tests/models/test_user.py
```

**复杂项目示例**：
```markdown
# 任务清单 - <功能名称>

## 复杂度级别：复杂
## 任务粒度：1-3分钟/任务

## 任务1：创建User类骨架
- 文件：`src/models/user.py`
- 时间：1分钟
- 步骤：
  1. 创建文件 src/models/user.py
  2. 定义空User类
- 验证：pytest tests/models/test_user.py::test_user_class_exists

## 任务2：添加id字段
- 文件：`src/models/user.py`
- 时间：1分钟
- 步骤：
  1. 添加id属性
  2. 添加类型注解
- 验证：pytest tests/models/test_user.py::test_user_id_field

## 任务3：添加name字段
- 文件：`src/models/user.py`
- 时间：1分钟
- 步骤：
  1. 添加name属性
  2. 添加验证逻辑
- 验证：pytest tests/models/test_user.py::test_user_name_field
```

### 关键原则
- 根据复杂度动态调整任务粒度
- 指定精确文件路径
- 包含完整代码（无TODO或占位符）
- 明确验证步骤
- 任务时间必须在预估范围内

## subagent-driven-development - 多智能体并行开发

### 概览
将任务分发给多个子智能体，每个负责一个独立的子任务，通过两阶段审查确保质量。

### 触发条件
- 任务可分解为多个独立的原子任务
- 需要加速开发进度
- 任务之间有低耦合度

### 执行步骤

1. **分配子任务**
   - 为每个子任务分配一个子智能体
   - 每个子智能体收到明确的任务描述和文件路径
   - 子智能体之间无直接通信，通过主智能体协调

2. **子智能体工作**
   - 每个子智能体独立完成其任务
   - 遵循 test-driven-development
   - 生成完整的代码（无TODO或占位符）

3. **两阶段审查**

   **阶段1：规格符合性审查**
   - 检查：是否完全实现了任务描述
   - 检查：文件路径是否正确
   - 检查：代码是否完整（无TODO）
   - 输出：通过/不通过，附评论

   **阶段2：代码质量审查**
   - 检查：代码可读性、命名规范
   - 检查：错误处理是否完善
   - 检查：是否有不必要的复杂性
   - 输出：通过/不通过，附评论

4. **迭代优化**
   - 如果任一阶段不通过，返回子智能体修改
   - 最多允许2轮迭代
   - 2轮后仍不通过，主智能体接管

### 输出格式
```markdown
# 多智能体开发协调

## 子任务分配
- 子智能体1：创建用户模型（3分钟）
- 子智能体2：创建数据库迁移（2分钟）
- 子智能体3：编写单元测试（3分钟）

## 审查结果

### 子智能体1
- 阶段1（规格）：✅ 通过
- 阶段2（质量）：⚠️ 需改进
  - 评论：缺少email字段的验证
  - 迭代1：已修复

### 子智能体2
- 阶段1（规格）：✅ 通过
- 阶段2（质量）：✅ 通过

### 子智能体3
- 阶段1（规格）：✅ 通过
- 阶段2（质量）：✅ 通过

## 最终状态
所有子任务完成，准备集成测试
```

### 关键原则
- 子任务必须独立，低耦合
- 每个子任务时间在预估范围内
- 两阶段审查：规格 → 质量
- 最多2轮迭代优化

## test-driven-development - 测试驱动开发

### 概览
强制执行 RED-GREEN-REFACTOR 循环，确保代码质量并通过自动化测试验证。

### 触发条件
- 任何编码工作
- 新功能实现
- Bug修复

### 执行步骤

1. **RED 阶段：编写失败测试**
   - 先编写测试用例，描述期望行为
   - 运行测试，确认失败（测试正确描述了需求）
   - **绝对禁止**在此阶段编写任何实现代码

2. **GREEN 阶段：最小化实现**
   - 编写最少量的代码使测试通过
   - **删除测试之前的所有代码**（TDD核心原则）
   - 不关心代码质量，只关心通过测试
   - 运行测试，确认通过

3. **REFACTOR 阶段：优化代码**
   - 重构代码，提升可读性、可维护性
   - 确保测试仍然通过
   - 重复重构直到满意

4. **循环**
   - 返回RED阶段，编写下一个测试
   - 重复循环直到功能完成

### 输出格式示例
```python
# 步骤1：RED - 编写测试
def test_user_creation():
    user = User(name="Alice", email="alice@example.com")
    assert user.id is not None
    assert user.name == "Alice"

# 运行：pytest  → 失败（User类不存在）

# 步骤2：GREEN - 最小实现
class User:
    def __init__(self, name, email):
        self.id = str(uuid.uuid4())
        self.name = name
        self.email = email

# 运行：pytest  → 通过

# 步骤3：REFACTOR - 优化
class User:
    def __init__(self, name: str, email: str):
        self.id = str(uuid.uuid4())
        self._validate_email(email)
        self.name = name
        self.email = email

    def _validate_email(self, email: str):
        if "@" not in email:
            raise ValueError("Invalid email")

# 运行：pytest  → 通过
```

### 关键原则
- **强制循环**：RED → GREEN → REFACTOR，不可跳跃
- **删除测试前的代码**：GREEN阶段必须删除测试前的实现代码
- **小步前进**：每次只写一个测试，使其通过，然后重构
- **测试优先**：先写测试，再写代码

### 反模式
- ❌ 先写代码，再写测试
- ❌ 写多个测试，然后一次性实现
- ❌ GREEN阶段优化代码（应该在REFACTOR阶段）
- ❌ 跳过REFACTOR阶段

## requesting-code-review - 代码审查（增强对抗性审查）

### 概览
在任务之间进行系统化代码审查，对照实施计划检查，强制发现问题（对抗性审查）。

### 执行步骤

1. **对照计划审查**
   - 读取 `docs/implementation-plan.md`
   - 检查是否实现了所有计划内容
   - 检查是否有遗漏或超出范围

2. **对抗性审查（新增）**
   - 强制必须找到问题，不允许"看起来不错"
   - 详见 [references/collaboration-skills-enhanced.md](references/collaboration-skills-enhanced.md) 中的 adversarial-review 部分

3. **质量检查清单**
   - 命名清晰且一致
   - 函数单一职责
   - 错误处理完善
   - 无重复代码（DRY原则）
   - 测试覆盖充分
   - 代码可读性良好

4. **严重性问题识别**
   - 仅报告阻碍继续开发的严重问题
   - 轻微问题可以记录但不阻塞
   - 提供具体的修复建议

5. **生成审查报告**

详细内容见：[references/collaboration-skills-enhanced.md](references/collaboration-skills-enhanced.md)

### 关键原则
- 严格对照计划，不超范围
- **对抗性审查：强制发现问题**
- 严重问题阻塞后续开发
- 提供具体修复建议
- 记录轻微问题但不阻塞

## finishing-a-development-branch - 分支收尾

### 概览
所有任务完成后，验证测试、清理工作区、决定合并策略（merge/PR/keep/discard）。

### 触发条件
- 所有任务清单完成
- 所有代码审查通过

### 执行步骤

1. **完整测试套件**
   ```bash
   pytest  # 运行所有测试
   ```
   - 确保所有测试通过
   - 检查测试覆盖率（目标 >80%）

2. **代码格式化**
   ```bash
   black .
   flake8 .
   ```
   - 确保代码风格一致
   - 修复所有linter警告

3. **检查未提交更改**
   ```bash
   git status
   ```
   - 确保所有更改已提交
   - 删除临时文件

4. **生成总结报告**
   - 功能描述
   - 实现的任务
   - 测试结果
   - 遗留问题

5. **决定合并策略**
   - **Merge**：小功能，无争议，直接合并
   - **PR**：中大功能，需要团队审查
   - **Keep**：WIP，保留分支继续开发
   - **Discard**：实验失败，放弃分支

### 输出格式

详细内容见原版 core-workflows.md

### 关键原则
- 所有测试必须通过
- 代码风格必须一致
- 清理所有临时文件
- 明确合并策略
- 生成完整报告

## complexity-assessment - 复杂度评估（新增）

### 概览
在进入设计或分析阶段前，评估项目复杂度以动态调整任务粒度。

### 评估维度

1. **功能复杂度**
   - 功能点数量：1-3（简单）、4-10（中等）、10+（复杂）
   - 依赖关系：单一模块、跨模块、跨系统

2. **技术复杂度**
   - 技术栈：单一技术、2-3个技术、多技术栈集成
   - 集成点：无外部集成、1-2个集成、多个复杂集成

3. **业务复杂度**
   - 业务规则：简单规则、中等复杂度规则、复杂业务逻辑
   - 约束条件：少量约束、中等约束、严格约束

### 复杂度级别

**简单级别**
- 1-3个功能点，单一技术栈
- 任务粒度：5-10分钟/任务
- 规划深度：基础PRD，简单故事

**中等级别**
- 4-10个功能点，2-3个技术栈
- 任务粒度：2-5分钟/任务
- 规划深度：完整PRD，详细故事

**复杂级别**
- 10+功能点，多技术栈，复杂集成
- 任务粒度：1-3分钟/任务
- 规划深度：完整PRD + 架构文档 + 详细故事

### 输出格式

```markdown
## 复杂度评估

### 功能复杂度
- 功能点数量：6
- 依赖关系：跨模块
- 评分：中等

### 技术复杂度
- 技术栈：3个（React, Node.js, PostgreSQL）
- 集成点：2个（第三方API, CDN）
- 评分：中等

### 业务复杂度
- 业务规则：基础规则
- 约束条件：少量约束
- 评分：简单

### 综合复杂度
**级别**：中等

### 调整建议
- 任务粒度：2-5分钟/任务
- 规划深度：完整PRD，详细故事
- 审查深度：基础审查
```

## product-brief - 产品简报（新增）

### 概览
在设计细化后、PRD生成前，创建产品简报以捕获战略愿景。

### 内容结构

```markdown
# 产品简报

## 战略愿景
- 产品长期愿景和目标
- 与整体产品战略的关系

## 目标用户
- 主要用户群体
- 用户画像和需求
- 用户痛点

## 成功指标
- 如何衡量功能成功
- 关键性能指标（KPI）
- 业务影响

## 竞争分析
- 竞争对手功能
- 差异化优势

## 约束条件
- 时间约束
- 资源约束
- 技术约束
```

### 保存位置
- 文件：`tasks/product-brief.md`

### 关键原则
- 确保PRD与战略目标一致

## implementation-readiness-check - 实施就绪检查（新增）

### 概览
在进入自主循环前，执行实施就绪检查。

### 检查项

#### PRD完整性
- [ ] 所有章节完整
- [ ] 无歧义描述
- [ ] 验收标准具体且可验证

#### 依赖清晰度
- [ ] 故事间依赖关系明确
- [ ] 外部依赖已识别
- [ ] 阻塞因素已列出

#### 故事大小合理性
- [ ] 所有故事可在单次迭代完成
- [ ] 故事粒度一致
- [ ] 无过大的任务

#### 技术可行性
- [ ] 技术方案可行
- [ ] 无重大技术风险
- [ ] 已考虑性能和安全

### 输出格式

```markdown
## 实施就绪检查

### 检查结果：PASS

### 检查项
- [x] PRD完整性：完整
- [x] 依赖清晰度：清晰
- [x] 故事大小合理性：合理
- [x] 技术可行性：可行

### 发现的问题
无

### 建议
可以进入自主循环
```

### 决策标准
- **PASS**：可以进入自主循环
- **CONCERNS**：解决后可以进入
- **FAIL**：返回PRD阶段重新设计

## 总结

核心工作流强调：
1. **设计优先**：brainstorming确保需求理解
2. **复杂度自适应**：根据复杂度动态调整
3. **任务分解**：原子任务，明确边界
4. **TDD驱动**：质量保证
5. **对抗性审查**：强制发现问题
6. **严格验证**：每个阶段验证
