# Frontend 重构 PRD

## 1. 概述

本 PRD 描述了对起了吗 App Frontend 的系统性重构，旨在提高代码质量、减少重复、增强可维护性，并为未来功能扩展奠定坚实基础。

**问题陈述**: 当前代码存在大量重复（违反 DRY 原则），缺乏抽象层，状态管理模式不统一，数据模型组织不当，缺乏测试覆盖。

## 2. 目标

- 消除代码重复，实现 DRY（Don't Repeat Yourself）原则
- 建立统一的抽象层和基础组件
- 标准化状态管理模式
- 改善代码组织和结构
- 提升代码可维护性和可测试性
- 建立基础测试框架

## 3. 重构目标

### RG-001: 创建统一的状态管理抽象层
**描述**: 建立基础状态类和通知器抽象，消除各 provider 中的重复代码

**接受标准**:
- 创建 `BaseState` 类，包含通用的 status、errorMessage 字段
- 创建 `BaseNotifier` 抽象类，实现通用的加载、刷新、错误处理逻辑
- 至少 4 个现有 provider 继承自新的基类
- 代码行数减少至少 30%

### RG-002: 统一状态枚举定义
**描述**: 替换所有自定义的状态枚举，使用统一的 LoadingState 枚举

**接受标准**:
- 创建统一的 `LoadingState` 枚举（initial, loading, loaded, error）
- 替换所有模块中的自定义状态枚举（ContactsStatus, DevicesStatus, HealthStatus 等）
- 所有 provider 使用统一的 LoadingState
- 枚举定义集中在一个文件中

### RG-003: 创建统一的 API 基类
**描述**: 建立 BaseApi 类，封装通用的 HTTP 请求和错误处理逻辑

**接受标准**:
- 创建 `BaseApi` 类，提供通用的 GET、POST、PUT、DELETE 方法
- 实现统一的错误处理和日志记录
- 至少 4 个 API 类继承自 BaseApi
- API 调用代码行数减少至少 40%

### RG-004: 分离数据模型
**描述**: 将数据模型从 API 服务文件中分离出来，创建独立的 models 目录

**接受标准**:
- 创建 `lib/core/models/` 目录
- 将所有数据模型（Contact, Device, HealthRecord, Medication 等）迁移到 models 目录
- 创建单独的 model 文件（contacts_models.dart, devices_models.dart 等）
- API 文件仅包含服务逻辑，不包含数据模型定义
- 文件大小减少，代码更易读

### RG-005: 统一错误处理机制
**描述**: 建立统一的异常类和错误处理策略

**接受标准**:
- 创建自定义异常类（ApiException, NetworkException, ValidationException）
- 实现统一的错误格式（code, message, details）
- 更新所有 provider 使用统一异常处理
- 错误消息格式一致

### RG-006: 改善配置管理
**描述**: 支持多环境配置，提高配置灵活性

**接受标准**:
- 创建环境配置枚举（dev, staging, prod）
- 实现 `EnvironmentConfig` 类，根据环境返回不同配置
- 支持 API 基础 URL、超时时间等参数的动态配置
- 添加配置验证逻辑

### RG-007: 优化代码组织结构
**描述**: 调整目录结构，提高代码可发现性

**接受标准**:
- 创建 `lib/core/models/` 目录存放通用数据模型
- 创建 `lib/core/exceptions/` 目录存放异常类
- 创建 `lib/core/constants/` 目录存放常量定义
- 创建 `lib/core/extensions/` 目录存放扩展方法
- 每个功能模块保持现有结构，但使用共享的核心组件

### RG-008: 建立测试框架
**描述**: 创建测试基础结构和关键组件的单元测试

**接受标准**:
- 设置测试目录结构（test/unit, test/widget, test/integration）
- 为 BaseState、BaseNotifier、BaseApi 编写单元测试
- 为至少 3 个核心 provider 编写单元测试
- 测试覆盖率至少达到 60%
- 添加测试运行脚本

## 4. 技术需求

1. **TR-001**: BaseState 类必须支持泛型，允许子类添加自定义字段
2. **TR-002**: BaseNotifier 必须实现通用的 refresh() 和 clearError() 方法
3. **TR-003**: BaseApi 必须支持请求重试机制（可选配置）
4. **TR-004**: 数据模型必须实现 equals() 和 hashCode() 方法
5. **TR-005**: 异常类必须包含详细的错误信息和堆栈跟踪
6. **TR-006**: 配置类必须支持从环境变量读取配置
7. **TR-007**: 测试必须使用 mockito 和 flutter_test 框架

## 5. 非目标

以下内容不在本次重构范围内：
- 添加新功能
- UI/UX 改进
- 性能优化（除非是重构的直接结果）
- E2E 测试
- 国际化改进
- 深度链接和路由优化

## 6. 设计考虑

### 6.1 架构决策
- 保持现有 Riverpod 状态管理方案
- 不引入新的状态管理库
- 保持现有的功能模块结构（features/ 目录）
- 渐进式重构，确保每个阶段代码可运行

### 6.2 可复用现有组件
- 保持现有的 ApiClient 单例
- 保持现有的路由配置
- 保持现有的主题系统
- 保持现有的拦截器（auth, logging, token）

### 6.3 迁移策略
- 先创建新的抽象层，再逐步迁移现有代码
- 每次迁移一个模块，确保测试通过
- 保持向后兼容性，避免破坏性变更

## 7. 技术考虑

### 7.1 已知约束
- Dart 3.2+ 语法和特性
- Flutter SDK 版本要求
- Riverpod 3.2.1 API
- Dio 5.8.0 网络库

### 7.2 依赖关系
- BaseState 依赖现有枚举和类型系统
- BaseNotifier 依赖 Riverpod 的 Notifier API
- BaseApi 依赖 Dio 的 Response 类型
- 测试框架依赖 mockito 和 flutter_test

### 7.3 性能要求
- 重构后不应引入显著的性能下降
- API 调用开销增加应控制在 5% 以内
- 状态更新性能应保持或提升

## 8. 成功指标

- 代码行数减少至少 30%
- 代码重复度（通过工具测量）降低至少 50%
- 单元测试覆盖率达到 60%
- Flutter analyze 无新的警告或错误
- 重构后的应用功能与重构前完全一致
- 代码可读性评分（人工评审）提升至少 20%

## 10. 优先级排序

**高优先级**（必须完成）:
- RG-001: 创建统一的状态管理抽象层
- RG-002: 统一状态枚举定义
- RG-003: 创建统一的 API 基类
- RG-004: 分离数据模型

**中优先级**（应该完成）:
- RG-005: 统一错误处理机制
- RG-006: 改善配置管理
- RG-007: 优化代码组织结构

**低优先级**（可以延后）:
- RG-008: 建立测试框架

## 11. 实施计划

重构将分为以下阶段进行：

**Phase 1: 基础设施**（RG-001, RG-002）
- 创建 BaseState 和 LoadingState
- 创建 BaseNotifier 抽象
- 编写单元测试

**Phase 2: API 层**（RG-003, RG-004）
- 创建 BaseApi 类
- 分离数据模型
- 迁移 API 类

**Phase 3: 错误处理和配置**（RG-005, RG-006）
- 创建异常类
- 实现统一错误处理
- 改善配置管理

**Phase 4: 代码组织**（RG-007）
- 优化目录结构
- 整理常量和扩展

**Phase 5: 测试**（RG-008）
- 编写单元测试
- 提高覆盖率
- 添加测试脚本
