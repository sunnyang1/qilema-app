# 产品需求文档：修复代码审查问题

## 引言/概述

本文档定义了修复"起了吗 App"后端代码审查中发现的所有问题的重构任务。这些问题的优先级从 P0（严重）到 P3（低），涉及安全漏洞、类型系统破坏、并发问题、代码质量等多个方面。

**审查结果摘要**：
- 18 个文件修改，359 行新增，54 行删除
- 发现 1 个严重安全漏洞（P0）
- 6 个高优先级问题（P1）
- 4 个中等优先级问题（P2）
- 2 个低优先级问题（P3）

**总体评估**：REQUEST_CHANGES（需要修改）

## 目标

1. **安全性**：消除所有安全漏洞（SECRET_KEY 泄露、IDOR、竞态条件）
2. **类型安全**：恢复类型系统的一致性，确保类型注解与实际返回值匹配
3. **代码质量**：消除代码异味（DRY 违规、手动映射、重复代码）
4. **可维护性**：改进代码结构，提升长期可维护性
5. **文档完善**：重新启用 API 文档，提升开发体验

## 重构目标

### P0 - Critical Issues

#### US-001: 移除硬编码的 SECRET_KEY

**描述**：作为系统管理员，我希望 JWT 签名密钥从环境变量加载而非硬编码在代码中，以防止密钥泄露导致的安全漏洞。

**验收标准**：
- `backend/app/core/config.py` 中的 SECRET_KEY 默认为空字符串
- SECRET_KEY 必须通过环境变量或 .env 文件设置
- 添加验证逻辑，拒绝空值或不安全的默认值
- 最小长度要求：64 字符
- 提供清晰的错误消息，指导用户如何生成安全密钥
- 更新文档说明 SECRET_KEY 的配置方法

**优先级**: 1

---

### P1 - High Priority Issues

#### US-002: 恢复 get_current_user 返回 User ORM 对象

**描述**：作为开发者，我希望 `get_current_user` 函数返回 User ORM 对象而非字典，以保持类型系统的一致性。

**验收标准**：
- `backend/app/core/security.py` 中的 `get_current_user` 返回 `User` 类型
- 返回类型注解为 `async def get_current_user(...) -> User`
- 保持现有的认证逻辑不变
- 确保 User 对象的所有关系和方法可用
- 添加类型检查，确保无类型错误

**优先级**: 2

---

#### US-003: 创建用户数据的 Pydantic 序列化方法

**描述**：作为开发者，我希望有一个统一的方法将 User ORM 对象序列化为字典，以便在 API 响应中使用。

**验收标准**：
- 创建 `user_to_dict(user: User) -> dict` 函数
- 使用 Pydantic 模式进行序列化
- 排除敏感字段（password_hash）
- 处理日期时间的 ISO 格式转换
- 处理枚举类型的值提取
- 添加单元测试验证序列化逻辑

**优先级**: 3

---

#### US-004: 修复 register 函数使用 Pydantic 模型

**描述**：作为开发者，我希望 `register` 函数使用 Pydantic 模型而非 dict 进行参数验证，以利用自动验证和文档生成功能。

**验收标准**：
- 创建 `UserRegisterRequest` Pydantic 模型
- 包含必需字段：phone, password, name
- 包含可选字段：nickname
- 添加字段验证（手机号格式、密码强度）
- 更新 `register` 函数签名接受 Pydantic 模型
- 移除手动字段验证代码
- 确保类型检查通过

**优先级**: 4

---

#### US-005: 添加签到的唯一约束

**描述**：作为系统，我希望防止同一用户在同一天多次签到，以避免 TOCTOU 竞态条件。

**验收标准**：
- 在 `CheckIn` 模型中添加唯一约束：(user_id, checkin_date)
- 更新数据库迁移脚本
- 修改 `create_checkin` 方法使用 try/except 处理唯一约束违反
- 返回清晰的错误消息："今天已经签到过了"
- 添加并发测试验证唯一约束有效

**优先级**: 5

---

#### US-006: 修复 IDOR 漏洞（SOS 操作）

**描述**：作为系统，我希望 SOS 服务使用认证用户的 ID 而非用户提供的 ID，以防止 IDOR（不安全的直接对象引用）漏洞。

**验收标准**：
- 修改 `create_sos_request` 接受 `user_id` 参数（从认证获取）
- 移除 `sos_data.user_id` 的使用
- 更新 API 层传递认证用户 ID
- 添加单元测试验证用户无法创建其他用户的 SOS
- 审计所有接受 user_id 参数的服务方法

**优先级**: 6

---

### P2 - Medium Priority Issues

#### US-007: 替换 health_records 手动字典映射

**描述**：作为开发者，我希望 health_records API 使用 Pydantic 模式序列化而非手动字典映射，以减少代码重复并提高可维护性。

**验收标准**：
- 创建 `HealthRecordResponse` Pydantic 模型
- 创建 `MedicalHistoryResponse`, `MedicationResponse`, `AllergyResponse` 模型
- 在 `create_health_record` 中使用 `HealthRecordResponse.model_validate()`
- 在 `get_health_record` 中使用嵌套模型序列化
- 移除所有手动字典映射代码
- 确保类型检查通过
- 添加单元测试验证序列化结果正确

**优先级**: 7

---

**验收标准**：
- 在 `get_health_record` 方法中使用 `joinedload`
- 加载 `medical_histories`, `medications`, `allergies` 关系
- 添加查询日志验证 N+1 问题已解决
- 确保性能测试通过（单次查询获取所有数据）
- 添加注释说明使用 eager loading 的原因

**优先级**: 8

## 设计考虑

### 架构决策

1. **类型安全优先**：所有修复都优先考虑类型系统的一致性
2. **向后兼容**：确保 API 响应格式保持兼容
3. **渐进式修复**：每个用户故事独立可测试，可单独部署
4. **测试驱动**：每个修复都包含相应的单元测试

### 可复用的现有组件

1. `app.core.response_builder.ApiResponseBuilder` - 统一响应格式
2. `app.core.security` - 认证相关函数
3. `app.schemas.*` - 现有的 Pydantic 模型

### 数据流

```
认证层 → 服务层 → ORM 层
    ↓
序列化层 → API 响应
```

### 错误处理

- 所有错误使用标准异常类
- 错误消息对用户友好
- 敏感信息不在错误消息中暴露
- 所有错误都记录日志

## 技术考虑

### 已知约束

1. **FastAPI 框架**：使用 FastAPI 的依赖注入和类型系统
2. **SQLAlchemy ORM**：使用 ORM 进行数据库操作
3. **Pydantic v2**：使用 Pydantic v2 进行数据验证和序列化
4. **Python 3.12**：使用 Python 3.12 特性

### 依赖项

- FastAPI: ^0.104.0
- SQLAlchemy: ^2.0.0
- Pydantic: ^2.0.0
- Pydantic Settings: ^2.0.0

### 性能需求

1. API 响应时间 < 500ms（P95）
2. 数据库查询次数最小化（避免 N+1）
3. 内存使用稳定（无内存泄漏）

2. **类型检查**：`mypy` 检查无错误
