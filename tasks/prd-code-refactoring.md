# 起了吗App代码重构PRD

## 1. 概述

本文档定义了对起了吗App进行代码重构的产品需求，旨在提升代码质量、一致性和可维护性。

## 2. 重构目标

### 2.1 总体目标
- 消除代码重复 (DRY原则)
- 提升代码一致性
- 降低耦合度
- 确保测试100%通过

### 2.2 具体目标
- 测试通过率保持100%
- 代码重复率降低50%+
- 统一API响应格式
- 统一错误处理机制

## 3. 用户故事

### US-001: 提取服务基类
**描述**: 作为开发者，我想要一个通用的服务基类，统一所有服务的CRUD操作，避免重复代码。

**验收标准**:
- [ ] 创建 BaseService 基类，包含通用的 CRUD 方法
- [ ] 所有现有服务类继承自 BaseService
- [ ] 基类支持通用的查询、创建、更新、删除操作
- [ ] 基类提供统一的缓存管理机制
- [ ] 所有测试通过

### US-002: 统一API响应格式
**描述**: 作为开发者，我想要统一的API响应格式，使前端能够一致地处理响应。

**验收标准**:
- [ ] 创建统一的响应包装器
- [ ] 所有API端点返回统一格式的响应
- [ ] 响应包含 success, message, data 字段
- [ ] 错误响应也使用统一格式
- [ ] 所有测试通过

### US-003: 规范化错误处理
**描述**: 作为开发者，我想要统一的错误处理机制，避免在API层重复编写错误处理代码。

**验收标准**:
- [ ] 创建全局异常处理器
- [ ] 自定义异常类体系
- [ ] 所有API端点使用统一异常处理
- [ ] 错误响应包含详细的错误信息
- [ ] 所有测试通过

### US-004: 统一时间戳使用
**描述**: 作为开发者，我想要统一的时间戳处理方式，避免时区问题和数据不一致。

**验收标准**:
- [ ] 所有时间戳使用 datetime.utcnow()
- [ ] 修复现有代码中的时间戳不一致问题
- [ ] 确保数据库中时间戳格式一致
- [ ] 所有测试通过

### US-005: 服务层规范化
**描述**: 作为开发者，我想要统一的服务层规范，避免实例方法和静态方法混用。

**验收标准**:
- [ ] 统一服务类方法为静态方法或类方法
- [ ] 移除不必要的构造函数
- [ ] 统一方法命名规范
- [ ] 所有测试通过

### US-006: 消除重复代码
**描述**: 作为开发者，我想要消除代码中的重复逻辑，提高可维护性。

**验收标准**:
- [ ] 提取通用的权限检查逻辑
- [ ] 提取通用的响应包装逻辑
- [ ] 提取通用的缓存操作逻辑
- [ ] 代码重复率降低50%以上
- [ ] 所有测试通过

## 4. 技术需求

### 4.1 依赖项
- Python 3.9+
- FastAPI
- SQLAlchemy 2.0+
- Pydantic v2

### 4.2 技术要求
- 保持向后兼容
- 所有现有测试必须通过
- 不破坏现有API接口

## 5. 非目标

- 不添加新功能
- 不修改数据库结构
- 不修改API端点URL
- 不修改请求/响应的数据结构

## 6. 成功指标

1. 测试通过率: 100%
2. 代码重复率: 降低50%+
3. 代码行数: 减少20%+
4. 圈复杂度: 降低30%

## 7. 风险与挑战

1. 重构过程中可能引入新的bug
2. 需要确保所有测试覆盖关键路径
3. 需要保持API向后兼容

## 8. 实施计划

1. **阶段1**: 创建基础设施 (US-001, US-002, US-003)
2. **阶段2**: 服务层重构 (US-005)
3. **阶段3**: 消除重复代码 (US-006)
4. **阶段4**: 时间戳统一 (US-004)
5. **阶段5**: 全面测试验证
